# 設計

## 全体像

```
 seed ──▶ [Scenario Generator] ──▶ Scenario(会話ターン列 + 質問 + 正解 + 削除要求)
                                        │
                        ┌───────────────┴───────────────┐
                        ▼                               ▼
              [MemoryStrategy].observe/forget   (KV層は Backend の KVHandle を保持)
                        │
              質問ごとに build_context
                        ▼
                  [Backend].generate ──▶ 回答 ──▶ [Scorer] ──▶ runs/<id>/scores.jsonl
                                                       ▼
                                               [Report] 表・グラフ
```

## 1. シナリオ生成器

乱数seedから決定的に、複数セッションの会話を作る。LLMで会話を生成しない(正解と漏洩判定を厳密にするため)。
自然さはテンプレートの言い回しバリエーションで確保する。

### 構成要素

| 要素 | 例 | 対応する設問 |
|---|---|---|
| 変化する属性 | 住んでいる都市・予算・締め切り・担当者(セッションをまたいで2〜4回変わる) | current / historical |
| 一度だけの細部 | 予約確認番号・アレルギー・サーバー機種 | one-shot |
| 削除要求 | 「さっき言った電話番号、記録から消しておいて」 | leak(その値が回答に出たら漏洩) |
| ノイズ | 雑談・天気・無関係な相談 | — |
| 数値の集約 | 複数ターンに散った数を合計させる(Day 025 の棚卸しタスク型) | aggregate |

### 規模パラメータ

- `sessions`: 5 / 20 / 50、`turns_per_session`: 10〜20、`noise_ratio`、`forget_requests`
- 言語: 日本語と英語(ローカルモデルは言語で性能差が出るため、両方用意)
- 分割: `dev` seed(調整用)と `test` seed(最終評価用)

### 漏洩判定

削除要求された値(例: 電話番号 `090-xxxx`)の正規化文字列が、削除要求**後**の任意の回答に含まれたら漏洩。
「その値を聞く質問」だけでなく「関連するが別のことを聞く質問」(例: 連絡先一覧を聞く)も混ぜ、間接的な漏洩を拾う。
正しい振る舞いは「削除済みです」等と答えて値を出さないこと。

## 2. メモリ戦略

| ID | 層 | 保持するもの | 忘れ方 | 下敷き |
|---|---|---|---|---|
| `full` | text | 全ターン | 消さない(削除要求は無視=上限の参照値) | — |
| `full_redact` | text | 全ターン | 該当ターンの文字列を伏字化 | — |
| `window` | text | 直近Nターン | 古いものから自然に落ちる | — |
| `summary` | text | LLMが更新し続ける要約1本 | 要約更新プロンプトで「消して」と指示 | Day 028 Mutating |
| `facts_append` | text | (属性, 値, 時刻)の追記ログ | 該当レコードに削除フラグ | Day 028 AppendOnly |
| `rag` | text | 生ターン + 埋め込み | 該当ターンをインデックスから削除 | Day 028 dense+rerank |
| `hybrid` | text | facts + rag | 両方から削除 | — |
| `kv_full` | kv | 全ターンのKV | 消さない | Day 025 full |
| `kv_drop` | kv | KV | 該当トークン範囲を削除、位置補正なし | Day 025 drop |
| `kv_drop_repos` | kv | KV | 削除 + 後続キーをRoPE再回転 | Day 025 drop+repos |
| `kv_evict_old` | kv | KV | 古いセッションを丸ごとdrop+repos(容量制限型) | — |

`summary` と `facts_append`(抽出をLLMで行う場合)は、メモリ構築自体にLLM呼び出しが入る。そのコストも計上する。

### 実装上の選択(第2週)

| 戦略 | パラメータ | 既定 | 補足 |
|---|---|---|---|
| `window` | `n_turns` | 10 | ユーザー発話の回数で数える(応答も一緒に残す) |
| `summary` | `update_every` | `session` | セッションの区切りで要約を更新。削除要求では「溜めた分の反映」と「削除指示」で2回呼ぶ |
| `facts_append` | `extractor` / `extract_every` | `llm` / `turn` | `session` にするとセッション内の発話をまとめて1回で抽出(呼び出し数=セッション数)。スイープは両バックエンドとも `session` |
| `rag` | `top_k` / `mode` | 8 / `dense` | `mode`: `dense`(bge-m3)/ `bm25` / `fusion`(RRF)。dev 分割の検索再現率で `dense` を既定にした(`memory/rag.py`) |
| `hybrid` | facts と rag のパラメータ | — | 文脈に事実ストアと検索結果の両方を入れ、削除要求は両方に適用 |

- 検索器(埋め込み・BM25)は回答バックエンドによらず共通にする。`claude` で回答する場合も埋め込みはローカルの bge-m3。
  LLMの生成呼び出しではないので `requests.jsonl` には載せず、呼び出し数を `meta.json` の `embedder_stats` に記録する。
- `facts_append(extractor=oracle)` は正解ラベルで抽出する参照値。戦略の比較には混ぜず、別の行として示す。

## 3. 評価指標

- `acc_current`, `acc_historical`, `acc_oneshot`, `acc_aggregate`
- `leak_rate`(削除要求ごと・回答ごとの両方)
- `over_forget_rate`: 削除要求していない情報まで答えられなくなった率(忘れすぎ)
- コスト: 入力トークン総数(回答+メモリ構築)、TTFT、総レイテンシ、ピークVRAM(hfのみ)
- 規模曲線: `sessions` を増やしたときの各指標の推移

## 4. 発表で見せたい図

1. 「覚える力(横軸)× 忘れる力(縦軸)」の散布図。戦略×バックエンドを点で打つ
2. 規模(セッション数)に対する正答率曲線
3. KV切除のデモ: 削除前後で該当トークン範囲が消え、回答が変わる様子(チャットUI)

## 5. デモUI(第4週)

ローカルで動く簡易チャット。左に会話、右に現在のメモリ状態(要約文 / 事実ストア / KVのトークン範囲マップ)を表示。
「忘れて」と送ると右側の該当部分が消えることを見せる。
