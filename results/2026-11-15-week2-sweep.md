## 気づき(dev 分割・小規模。結論として引用しない)

- **ollama の `full` は、規模が大きいほど削除済みの値を漏らした。** leak/request は日本語 33→67→83%、英語 0→33→67%(5→20→50セッション)。
  削除要求の発話は文脈に残っているが、長い文脈では守られなくなる。
- **値を文脈から消す戦略(`full_redact` / `rag` / `hybrid` / `facts_append` / `summary`)は、ollama ではどの規模でも漏洩 0%。**
  `full_redact` は `full` とほぼ同じ正答率で漏洩だけが消えた。
- ollama の `rag` は文脈が回答1回あたり約400トークン(日本語)と `full` の 1/5〜1/50 で、current は 83〜92%(日本語)と `full` 以上。
- ollama の `summary` は正答率が低い(日本語の current 8〜25%)。生ログでは、7B の要約が雑談を残し、変化の履歴を取り違え、事実を落としている
  (パイプラインの不具合ではない)。Day 028 の上書きメモリの historical が低かったことと同じ傾向。
- ollama の `facts_append`(LLM抽出)は `facts_append_oracle` との差が大きい(日本語5セッションの current 17% 対 92%)。差は抽出の質による損失。
- **claude は 50 セッションまで `full` でも漏らさなかった**(同じシナリオの ollama は 5/20/50 のすべてで leak/request 100%)。
  削除要求の発話が文脈にあれば守れる。ただし1シナリオ・繰り返しなしで、削除要求は各規模2件だけ。
- claude では `summary` も全規模で 100%(ollama は 0〜50%)。ollama で弱かった戦略の差は、モデルの能力によるところが大きい。
- **claude の `summary` は 50 セッションで要約が圧縮されなくなった。** 要約がセッションごとの記録(雑談も含む)になり 21,512 文字まで伸び、
  回答1回の入力は 20,601 トークンと `full`(34,778)の6割に達した。20セッションでは 452 文字だった。要約を更新し続ける方式は、
  正答率は保てても「小さく保つ」役目を果たさない場合がある。
- claude でも、検索系(`rag` / `hybrid`)は `full` の 1/40 の文脈(約830トークン)で同等の正答率だった。
- claude の in-tok/answer が ollama の約2倍なのは、Claude Code が足すシステムプロンプトの1文と環境情報ブロック、トークナイザの違いによる。
  バックエンド間でトークン数を直接比べない(docs/backends.md「バックエンド間の比較で気をつけること」)。

## 注意(揃えられない差・測定の癖)

- claude は温度・seed・最大出力トークンを指定できない。揺れは repeats=3 の範囲で示した。
- レスポンスキャッシュは run の中でも効く。`hybrid` の事実抽出は `facts_append` と全く同じ入力なので、2回目はキャッシュから返る。
  コスト(トークン数)は両方に計上しているが、**claude では両戦略が同じ抽出結果を共有している**(繰り返しごとに独立ではあるが、戦略間では独立でない)。
- ollama の latency は単独実行で測った(claude スイープとは時間をずらした。埋め込みが同じ Ollama サーバーを使うため)。
