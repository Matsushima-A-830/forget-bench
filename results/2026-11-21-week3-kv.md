## 設定

- シナリオ: 第2週の ollama スイープと同じ(dev 分割 seed 1000–1002 × 日英 × 5 / 20 / 50 セッション、各10〜20発話、
  属性4・一度だけの細部3・個人情報3(うち削除要求2)・集約4)。1つの (言語, 規模) の欄は、current 12問・削除要求6件など
- バックエンド: `hf`、`Qwen/Qwen2.5-3B-Instruct`(revision `aa8e72537993ba99e69dfaafa59ed015b17504d1`、下記)、bf16、
  `attn_implementation=eager`、prefill 512 トークンずつ、greedy、max_tokens 256。torch 2.15.0+cu132 / transformers 5.23.0、RTX 5060 Ti 16GB
- 戦略(12): テキスト層8(第2週と同じ設定)+ KV 層4
  - `kv_full`: 会話を発話ごとに KV キャッシュへ追記し、削除要求は無視する
  - `kv_drop`: 削除要求の対象発話のトークン範囲をキャッシュから切除する(後続のキーの回転はそのまま = naive)
  - `kv_drop_repos`: 同じく切除し、後続のキーを詰めた位置へ RoPE で再回転する(Day 025 の移植)
  - `kv_evict_old`: 直近2セッションより古いセッションの範囲を切除する(repos あり)。削除要求は無視する
- 埋め込み(`rag` / `hybrid`): Ollama の bge-m3(digest `790764642607…`)。**スイープ中ずっと Ollama 側で GPU に載ったまま**
  (約0.7GB。設計どおり。docs/backends.md)。回答用の LLM は Ollama に載せていない
- 比較の注意: 第2週の ollama は **7B**(`qwen2.5:7b-instruct`)、このスイープは **3B**。モデルが違うので ollama との比較は参考値。
  KV 層とテキスト層の比較は、このスイープ内(同じ 3B・同じ hf 実装)で行う

## 気づき

**1欄が小さい(current 12問・削除要求6件)ので、数ポイントの差は揺れの範囲として読む。繰り返しはしていない(greedy で1回)。**

1. **KV から切除すれば漏れない。** `kv_drop` / `kv_drop_repos` は全規模・日英で leak/request 0%。削除要求を無視する `kv_full` は
   `full` とほぼ同じだけ漏れる(en 100 / 83 / 50%、ja 100 / 0 / 0%。`full` は en 100 / 83 / 50%、ja 100 / 0 / 17%)。
   テキスト層で消す `full_redact` も 0% で、KV 層の切除はこれと同じ効果になった。消しすぎ(over-forget)は drop 系が 0〜9%、`full_redact` が 0〜4%。
2. **KV の切除はテキストの削除と同じくらい覚えている。** `kv_drop_repos` と `full_redact` は 340問中 321問で正誤が一致
   (`kv_drop_repos` だけ正解 12、`full_redact` だけ正解 7)。どちらも 3B の地力で頭打ち(ja 50セッションの current は 33% と 17%)。
3. **naive drop でも壊れなかった。repos の差は小さい。** `kv_drop_repos` と `kv_drop` は 340問中 319問で正誤が一致
   (repos だけ正解 15、naive だけ正解 6)。回答文が一致したのは 180問で、位置のずれで出力自体は変わっている。
   このシナリオで切除するのは1シナリオあたり 45〜57 トークン(表2の dropped tok)だけで、後続のキーのずれも高々その程度。
   GPU テスト(`tests/test_kv_gpu.py`)で naive drop の生成が崩れた例とは条件が違う。切除量が大きい条件(長い発話の削除、
   `kv_evict_old` のような大きな切除を repos なしで行う)は、このスイープでは測っていない。
4. **`kv_full` と `full` は入力が完全に同じでも回答文が少し違う。** 340問すべてで、メッセージ数・文字数・文脈トークン数が一致した
   (`requests.jsonl` で確認)。正誤は 328問で一致、回答文は 261問で一致。KV 層は発話ごとに prefill し、テキスト層は 512 トークンずつ
   prefill するので、bf16 の丸めが変わり、greedy がそれを増幅したと考えている(この run では切り分けていない)。
   smoke(5セッション・9問)では全問一致していた。
5. **`kv_evict_old` は `window` のセッション版になった。** historical は全規模で 0%、current は 17〜83%。キャッシュは規模によらず
   約 900〜1,000 トークンで一定。日本語では消しすぎが多い(15 / 38 / 34%)。削除要求は無視するが、この run では漏洩は 0%だった
   (古いセッションごと消えたためと思われるが、削除対象の発話がどのセッションにあったかは集計していない)。
6. **コストの差は、キャッシュの使い回しによるもの。** 50セッションで、`full` の回答は 1回 52.22秒(en)/ 62.87秒(ja)、
   `kv_full` は 1.50秒 / 1.87秒(TTFT は 50.87 / 61.10秒に対して 0.13 / 0.14秒)。1シナリオの所要時間は 1,027.5秒 / 1,236.8秒に対して
   161.8秒 / 180.1秒。テキスト層は質問ごとに約1.9万トークンを prefill し直すが、KV 層は会話を1回だけ prefill する(KV prefill tok ≈ 文脈長)。
   5セッションでは差は小さい(1.29秒と 0.61秒)。回答時のピーク VRAM も `full` 8,465 / 8,591MB に対して `kv_full` 6,915 / 6,975MB と低い。
   テキスト層は 512 トークンの塊を長い文脈に対して流すので eager の注意重みが大きくなる、という説明が考えられる(未確認)。
   **ただしこれは同じ会話に何問も続けて聞くこのベンチの形に有利な比較**で、テキスト層でも prefix キャッシュがあれば差は縮む。
7. **ollama(7B)との参考比較。** 同じシナリオで 3B は全体に弱い(`full` の en 5セッション current は 3B 75% / 7B 100%)。
   `rag` は 3B でも比較的保つ(en current 83 / 75 / 92%)。テキスト層の戦略の順位(`rag` / `hybrid` が上、`window` / `summary` が下)は
   7B と大きくは変わらない。モデルの大きさが違うので、バックエンド間の比較には使わない。
